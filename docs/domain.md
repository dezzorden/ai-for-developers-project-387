# Доменная модель сервиса «Запись на звонок»

## Владелец календаря

Единственный заранее заданный профиль, к календарю которого относятся все типы событий и бронирования. Владелец не регистрируется и не входит в систему.

Поля:

- `id` — неизменяемый идентификатор профиля;
- `name` — отображаемое имя;
- `timeZone` — часовой пояс IANA, в котором рассчитываются календарные даты и окно записи.

## Тип события

Шаблон встречи, создаваемый владельцем.

Поля:

- `id` — задаваемый владельцем уникальный строковый идентификатор;
- `title` — название;
- `description` — описание;
- `durationMinutes` — положительная длительность в минутах, не больше 24 часов;
- `createdAt` — момент создания.

Все созданные типы событий доступны гостям. Изменение и удаление типа события на первом этапе не поддерживаются.

## Слот

Вычисляемый, а не сохраняемый интервал, в который можно начать встречу выбранного типа. Начало слота лежит на 30-минутной сетке, окончание рассчитывается как `startAt + durationMinutes`. Регулярное доступное время владельца является заранее заданной конфигурацией сервера: ежедневно с 09:00 до 18:00 в часовом поясе владельца. Управление этим расписанием не входит в API первого этапа.

Слот доступен, если:

- его начало попадает в окно записи из 14 календарных дней, включая текущую дату владельца;
- весь интервал встречи входит в доступное время владельца;
- интервал не пересекается ни с одним существующим бронированием любого типа события;
- начало слота еще не наступило.

API передает моменты времени в UTC. Границы 14-дневного окна вычисляются в `Owner.timeZone` и возвращаются клиенту вместе со слотами.

## Бронирование

Зафиксированная встреча гостя с владельцем.

Поля:

- `id` — сгенерированный сервером UUID;
- `eventTypeId` — тип события;
- `eventTitle` — снимок названия типа события для отображения;
- `startAt` и `endAt` — интервал встречи в UTC;
- `guestName` и `guestEmail` — контактные данные гостя;
- `createdAt` — момент создания.

Сервер принимает только тип события, начало выбранного слота и данные гостя. Окончание встречи вычисляется сервером. Проверка доступности и создание бронирования выполняются атомарно: пересекающиеся бронирования запрещены даже для разных типов событий. При конкурентной попытке занять интервал только один запрос завершается успешно, остальные получают `409 Conflict`.

## Публичный сценарий гостя

1. Гость получает профиль владельца и список типов событий.
2. Гость выбирает тип события.
3. Клиент запрашивает доступные слоты этого типа на установленное сервером окно в 14 дней.
4. Гость выбирает слот и отправляет его начало, имя и email.
5. Сервер повторно проверяет тип события, окно записи и отсутствие пересечений.
6. Сервер возвращает созданное бронирование либо объяснимую ошибку: некорректные данные, неизвестный тип события, время вне окна или уже занятый интервал.

## Сценарий владельца

1. Владелец создает тип события с уникальным `id`, названием, описанием и допустимой длительностью.
2. Владелец запрашивает единый список будущих бронирований всех типов событий.
3. Бронирования возвращаются по возрастанию времени начала; отмена и изменение на первом этапе не поддерживаются.

Административные операции отделены маршрутом `/admin`, но в текущей версии не защищены авторизацией.
